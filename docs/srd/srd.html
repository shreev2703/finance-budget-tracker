1. INTRODUCTION

1.1 PROJECT PURPOSE

  • PROBLEM STATEMENT: COLLEGE STUDENTS AND YOUNG ADULTS OFTEN LOSE TRACK OF SMALL DAILY PURCHASES AND OVERSPEND THEIR MONTHLY ALLOWANCE OR PART-TIME INCOME. EXISTING OPTIONS ARE EITHER TEDIOUS MANUAL SPREADSHEETS OR PAID APPS THAT REQUIRE LINKING A BANK ACCOUNT.
  • PRODUCT VISION: FOR COLLEGE STUDENTS AND YOUNG ADULTS WHO STRUGGLE TO TRACK DAILY EXPENSES AND STICK TO A MONTHLY ALLOWANCE, LEDGERLOGIC IS A PERSONAL FINANCE AND BUDGET TRACKING WEB APPLICATION WHICH SIMPLIFIES DAILY TRANSACTION LOGGING AND PROVIDES INSTANT VISUAL INSIGHTS INTO SPENDING HABITS. UNLIKE COMPLEX MANUAL SPREADSHEETS OR PAID SUBSCRIPTION APPS THAT REQUIRE INVASIVE BANK ACCOUNT LINKING, OUR PRODUCT OFFERS A FAST, CLUTTER-FREE INTERFACE FOR MANUAL EXPENSE TRACKING AND GOAL SETTING WITHOUT SUBSCRIPTION FEES OR PRIVACY RISKS.

1.2 INTENDED AUDIENCE

  • TARGET AUDIENCE: PRIMARY USERS ARE COLLEGE STUDENTS AND YOUNG ADULTS MANAGING A FIXED MONTHLY ALLOWANCE OR PART-TIME INCOME. STAKEHOLDERS INCLUDE THESE END USERS, THE LEDGERLOGIC ENGINEERING TEAM, AND THE CSC 3100 INSTRUCTOR AS PROJECT CLIENT AND EVALUATOR.

1.3 PROJECT SCOPE

  • SCOPE: IN SCOPE: ACCOUNT REGISTRATION AND LOGIN; MANUAL LOGGING, EDITING, AND DELETING OF INCOME AND EXPENSE TRANSACTIONS; A DASHBOARD WITH TOTALS AND REMAINING BALANCE; A SPENDING-BY-CATEGORY CHART; FILTERED TRANSACTION HISTORY; AND PER-CATEGORY MONTHLY SPENDING LIMITS WITH AN 80% WARNING. OUT OF SCOPE: BANK ACCOUNT LINKING, AUTOMATIC TRANSACTION IMPORT, MULTI-CURRENCY SUPPORT, SHARED OR HOUSEHOLD BUDGETS, AND NATIVE MOBILE APPS.

4. NON-FUNCTIONAL REQUIREMENTS

4.1 DATA INTEGRITY & SECURITY

  • INTEGRITY: HANDLING ERRORS AND BAD DATA. THE API REJECTS INVALID INPUT WITH A CLEAR LIST OF ERRORS (HTTP 400): AMOUNTS MUST BE POSITIVE AND AT MOST $1,000,000, DATES MUST BE VALID (YYYY-MM-DD), AND A TRANSACTION'S CATEGORY MUST BELONG TO THE USER AND MATCH THE TRANSACTION TYPE. THE DATABASE ENFORCES THE SAME RULES WITH CHECK AND FOREIGN KEY CONSTRAINTS. MONEY IS STORED AS INTEGER CENTS TO AVOID ROUNDING ERRORS.
  • SECURITY: IMPLEMENT BCRYPT FOR PASSWORD HASHING AND ENVIRONMENT VARIABLES FOR DB CREDENTIALS. EVERY QUERY IS SCOPED TO THE LOGGED-IN USER, AND ALL SQL USES PARAMETERIZED QUERIES TO PREVENT SQL INJECTION.

4.2 PERFORMANCE & USABILITY

  • PERFORMANCE: THE DASHBOARD LOADS ITS TOTALS AND BUDGET STATUS FROM A SINGLE API CALL, AND API RESPONSES SHOULD RETURN IN UNDER 500 MS ON A LOCAL MACHINE.
  • USABILITY: LOGGING A TRANSACTION TAKES ONE SHORT FORM (AMOUNT, CATEGORY, DATE, OPTIONAL NOTE). ERRORS ARE SHOWN IN PLAIN LANGUAGE, BUDGET STATUS USES BOTH COLOR AND TEXT (E.G. "OVER BUDGET"), AND THE LAYOUT WORKS ON DESKTOP AND PHONE-WIDTH SCREENS.

5. SYSTEM ARCHITECTURE

5.1 REST API ENDPOINTS

  • REST ENDPOINTS: (LIST METHOD | URL | DESCRIPTION) — BASE URL: http://localhost:3001/api
  • IMPLEMENTED ENDPOINTS:
    • GET /api/transactions — FETCHES THE USER'S TRANSACTIONS, NEWEST FIRST.
    • POST /api/transactions — CREATES A NEW INCOME OR EXPENSE (RETURNS 400 WITH A LIST OF ERRORS IF INVALID).
    • GET /api/budgets/summary — FETCHES MONTHLY TOTALS AND EACH CATEGORY'S LIMIT, SPENT, REMAINING, AND STATUS (OK / WARNING / OVER).
    • GET /api/categories — FETCHES THE USER'S INCOME AND EXPENSE CATEGORIES WITH THIS MONTH'S LIMIT.
    • POST /api/budgets — SETS A MONTHLY LIMIT FOR AN EXPENSE CATEGORY (409 IF ONE ALREADY EXISTS).
    • PUT /api/budgets/:id — CHANGES A BUDGET'S MONTHLY LIMIT.
    • POST /api/categories — CREATES AN INCOME OR EXPENSE CATEGORY (409 IF THE NAME IS ALREADY USED).
    • PUT /api/categories/:id — RENAMES A CATEGORY.
    • DELETE /api/categories/:id — DELETES A CATEGORY AND ITS BUDGETS (409 IF IT STILL HAS TRANSACTIONS).
  • PLANNED ENDPOINTS:
    • PUT / DELETE /api/transactions/:id — EDITS OR DELETES A TRANSACTION (US-03).
    • GET /api/transactions?category=&from=&to= — FILTERS TRANSACTION HISTORY (US-06).
    • GET /api/reports/spending-by-category — FETCHES SPENDING PER CATEGORY FOR THE CHART (US-05).
    • POST /api/auth/register, POST /api/auth/login — CREATES AN ACCOUNT AND LOGS IN (US-07).

5.4 ARCHITECTURE & DESIGN PATTERNS

  • ARCHITECTURE: LAYERED ARCHITECTURE INSIDE A CLIENT-SERVER SYSTEM: REACT CLIENT → EXPRESS MIDDLEWARE → ROUTES → SERVICES → REPOSITORIES → DATABASE. NO EXTERNAL SYSTEMS.
  • DESIGN PATTERN: CHAIN OF RESPONSIBILITY (GANG OF FOUR), IMPLEMENTED AS THE EXPRESS MIDDLEWARE CHAIN.
  • DESIGN DECISIONS: SERVICE AND REPOSITORY LAYERS; SQLITE NOW WITH A MYSQL-COMPATIBLE SCHEMA; MONEY STORED AS INTEGER CENTS; BCRYPT LOGIN BUILT AFTER THE CORE BUDGETING FLOW; SHARED REACT STATE IN THE TOP-LEVEL COMPONENT.

1. INTRODUCTION

1.1 PROJECT PURPOSE

  • PROBLEM STATEMENT: COLLEGE STUDENTS AND YOUNG ADULTS OFTEN LOSE TRACK OF SMALL DAILY PURCHASES AND OVERSPEND THEIR MONTHLY ALLOWANCE OR PART-TIME INCOME. EXISTING OPTIONS ARE EITHER TEDIOUS MANUAL SPREADSHEETS OR PAID APPS THAT REQUIRE LINKING A BANK ACCOUNT.
  • PRODUCT VISION: FOR COLLEGE STUDENTS AND YOUNG ADULTS WHO STRUGGLE TO TRACK DAILY EXPENSES AND STICK TO A MONTHLY ALLOWANCE, LEDGERLOGIC IS A PERSONAL FINANCE AND BUDGET TRACKING WEB APPLICATION WHICH SIMPLIFIES DAILY TRANSACTION LOGGING AND PROVIDES INSTANT VISUAL INSIGHTS INTO SPENDING HABITS. UNLIKE COMPLEX MANUAL SPREADSHEETS OR PAID SUBSCRIPTION APPS THAT REQUIRE INVASIVE BANK ACCOUNT LINKING, OUR PRODUCT OFFERS A FAST, CLUTTER-FREE INTERFACE FOR MANUAL EXPENSE TRACKING AND GOAL SETTING WITHOUT SUBSCRIPTION FEES OR PRIVACY RISKS.

1.2 INTENDED AUDIENCE

  • TARGET AUDIENCE: PRIMARY USERS ARE COLLEGE STUDENTS AND YOUNG ADULTS MANAGING A FIXED MONTHLY ALLOWANCE OR PART-TIME INCOME. STAKEHOLDERS INCLUDE THESE END USERS, THE LEDGERLOGIC ENGINEERING TEAM, AND THE CSC 3100 INSTRUCTOR AS PROJECT CLIENT AND EVALUATOR.

1.3 PROJECT SCOPE

  • SCOPE: IN SCOPE: ACCOUNT REGISTRATION AND LOGIN; MANUAL LOGGING, EDITING, AND DELETING OF INCOME AND EXPENSE TRANSACTIONS; A DASHBOARD WITH TOTALS AND REMAINING BALANCE; A SPENDING-BY-CATEGORY CHART; FILTERED TRANSACTION HISTORY; AND PER-CATEGORY MONTHLY SPENDING LIMITS WITH AN 80% WARNING. OUT OF SCOPE: BANK ACCOUNT LINKING, AUTOMATIC TRANSACTION IMPORT, MULTI-CURRENCY SUPPORT, SHARED OR HOUSEHOLD BUDGETS, AND NATIVE MOBILE APPS.

4. NON-FUNCTIONAL REQUIREMENTS

4.1 DATA INTEGRITY & SECURITY

  • INTEGRITY: The API rejects bad data with a clear error list (HTTP 400): amounts must be positive and at most $1,000,000, dates must be valid (YYYY-MM-DD), and a transaction's category must belong to the user and match the transaction type. The database enforces the same rules with CHECK and FOREIGN KEY constraints. Money is stored as integer cents to avoid rounding errors.
  • SECURITY: Implement bcrypt for password hashing and environment variables for DB credentials. Every query is scoped to the logged-in user's ID, so users can never read or change another user's data. All SQL uses parameterized queries to prevent SQL injection.

4.2 PERFORMANCE & USABILITY

  • PERFORMANCE: The dashboard loads its totals and budget status from a single API call, and API responses on a local machine should return in under 500 ms.
  • USABILITY: Logging a transaction takes one short form (amount, category, date, optional note). Validation errors are shown next to the form in plain language. Budget status uses both color and text (e.g. "Over budget"), so it doesn't rely on color alone. The layout works on desktop and phone-width screens.

5. SYSTEM ARCHITECTURE

LedgerLogic is a React single-page app that calls a Node.js/Express REST API. The API is layered: routes (HTTP) → services (validation and business rules) → repositories (SQL) → database. Source: packages/backend/src/ and packages/frontend/src/.

5.1 REST API ENDPOINTS

Base URL (local): http://localhost:3001/api. Requests and responses are JSON. Amounts are sent in dollars (amount) and returned in integer cents (…Cents).

5.4 ARCHITECTURE & DESIGN PATTERNS (TE4)

Full write-up with all TE3 and TE4 diagrams: docs/design/LedgerLogic-Design-Document-TE3-TE4.pdf in the repository.

  • Architecture: layered architecture inside a client-server system. React client → Express middleware → routes → services → repositories → SQLite/MySQL. The client always starts the request; each server layer only calls the layer below it.
  • External systems: none. Bank linking, payments, and third-party login are out of scope.
  • Design pattern (Gang of Four): Chain of Responsibility (implemented). Every request passes through a chain of Express middleware handlers (express.json → demoUser → apiRouter → notFound → errorHandler). Each handles one concern and calls next(). Swapping the demo user for real login (US-07) means replacing one handler.
  • Key design decisions: (1) service and repository layers instead of logic in routes; (2) SQLite now with a MySQL-compatible schema; (3) money stored as integer cents; (4) our own bcrypt login, built after the core budgeting flow; (5) shared React state in the top-level component instead of a state library.

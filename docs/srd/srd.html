1. INTRODUCTION

1.1 PROJECT PURPOSE

  • PROBLEM STATEMENT: COLLEGE STUDENTS AND YOUNG ADULTS OFTEN LOSE TRACK OF SMALL DAILY PURCHASES AND OVERSPEND THEIR MONTHLY ALLOWANCE OR PART-TIME INCOME. EXISTING OPTIONS ARE EITHER TEDIOUS MANUAL SPREADSHEETS OR PAID APPS THAT REQUIRE LINKING A BANK ACCOUNT.
  • PRODUCT VISION: FOR COLLEGE STUDENTS AND YOUNG ADULTS WHO STRUGGLE TO TRACK DAILY EXPENSES AND STICK TO A MONTHLY ALLOWANCE, LEDGERLOGIC IS A PERSONAL FINANCE AND BUDGET TRACKING WEB APPLICATION WHICH SIMPLIFIES DAILY TRANSACTION LOGGING AND PROVIDES INSTANT VISUAL INSIGHTS INTO SPENDING HABITS. UNLIKE COMPLEX MANUAL SPREADSHEETS OR PAID SUBSCRIPTION APPS THAT REQUIRE INVASIVE BANK ACCOUNT LINKING, OUR PRODUCT OFFERS A FAST, CLUTTER-FREE INTERFACE FOR MANUAL EXPENSE TRACKING AND GOAL SETTING WITHOUT SUBSCRIPTION FEES OR PRIVACY RISKS.

1.2 INTENDED AUDIENCE

  • TARGET AUDIENCE: PRIMARY USERS ARE COLLEGE STUDENTS AND YOUNG ADULTS MANAGING A FIXED MONTHLY ALLOWANCE OR PART-TIME INCOME. STAKEHOLDERS INCLUDE THESE END USERS, THE LEDGERLOGIC ENGINEERING TEAM, AND THE CSC 3100 INSTRUCTOR AS PROJECT CLIENT AND EVALUATOR.

1.3 PROJECT SCOPE

  • SCOPE: IN SCOPE: ACCOUNT REGISTRATION AND LOGIN, CHANGING THE PASSWORD, AND DELETING THE ACCOUNT; MANUAL LOGGING, EDITING, AND DELETING OF INCOME AND EXPENSE TRANSACTIONS; A DASHBOARD WITH TOTALS AND REMAINING BALANCE; A SPENDING-BY-CATEGORY CHART; FILTERED TRANSACTION HISTORY; AND PER-CATEGORY MONTHLY SPENDING LIMITS WITH AN 80% WARNING. OPTIONAL (STRETCH, US-10): CONNECTING A BANK THROUGH PLAID TO IMPORT TRANSACTIONS, OFF UNLESS PLAID KEYS ARE CONFIGURED. OUT OF SCOPE: MULTI-CURRENCY SUPPORT, SHARED OR HOUSEHOLD BUDGETS, AND NATIVE MOBILE APPS.

4. NON-FUNCTIONAL REQUIREMENTS

4.1 DATA INTEGRITY & SECURITY

  • INTEGRITY: HANDLING ERRORS AND BAD DATA. THE API REJECTS INVALID INPUT WITH A CLEAR LIST OF ERRORS (HTTP 400): AMOUNTS MUST BE POSITIVE AND AT MOST $1,000,000, DATES MUST BE REAL CALENDAR DAYS IN YYYY-MM-DD FORM (2026-02-30 IS REJECTED), RECORD IDS THAT CANNOT EXIST (SUCH AS abc OR 1.5) RETURN 404 OR 400 INSTEAD OF A SERVER ERROR, AND A TRANSACTION'S CATEGORY MUST BELONG TO THE USER AND MATCH THE TRANSACTION TYPE. THE DATABASE ENFORCES THE SAME RULES WITH CHECK AND FOREIGN KEY CONSTRAINTS. MONEY IS STORED AS INTEGER CENTS TO AVOID ROUNDING ERRORS. THESE RULES ARE COVERED BY THE AUTOMATED TESTS IN SECTION 9.
  • SECURITY: PASSWORDS ARE HASHED WITH BCRYPT AND NEVER RETURNED BY THE API. EVERY DATA ROUTE REQUIRES A SIGNED JWT THAT EXPIRES AFTER ONE DAY, AND THE SIGNING KEY COMES FROM THE TOKEN_SECRET ENVIRONMENT VARIABLE, NOT THE CODE. THE DATABASE CONNECTION STRING (DATABASE_URL) IS ALSO AN ENVIRONMENT VARIABLE, AND ONLY THE BACKEND CONNECTS TO THE DATABASE; THE WEBSITE NEVER RECEIVES DATABASE CREDENTIALS, AND ROW LEVEL SECURITY ON EVERY TABLE STOPS SUPABASE'S PUBLIC DATA API FROM READING OR CHANGING THE DATA. BANK CONNECTIONS (US-10): THE STUDENT SIGNS IN TO THEIR BANK INSIDE PLAID'S WINDOW, NEVER ON OUR SITE; THE PLAID SECRET AND ACCESS TOKENS NEVER REACH THE BROWSER; ACCESS TOKENS ARE STORED ENCRYPTED WITH AES-256-GCM; AND PLAID ERRORS ARE SHOWN AS A PLAIN MESSAGE WITHOUT TOKENS OR DETAILS. EVERY QUERY IS SCOPED TO THE LOGGED-IN USER, AND ALL SQL USES PARAMETERIZED QUERIES TO PREVENT SQL INJECTION. API RESPONSES ARE SENT WITH CACHE-CONTROL: NO-STORE SO FINANCIAL DATA DOES NOT STAY IN THE BROWSER CACHE.

4.2 PERFORMANCE & USABILITY

  • PERFORMANCE: THE DASHBOARD LOADS ITS TOTALS AND BUDGET STATUS FROM A SINGLE API CALL, AND API RESPONSES SHOULD RETURN IN UNDER 500 MS ON A LOCAL MACHINE.
  • USABILITY: LOGGING A TRANSACTION TAKES ONE SHORT FORM (AMOUNT, CATEGORY, DATE, OPTIONAL NOTE). ERRORS ARE SHOWN IN PLAIN LANGUAGE, BUDGET STATUS USES BOTH COLOR AND TEXT (E.G. "OVER BUDGET"), AND THE LAYOUT WORKS ON DESKTOP AND PHONE-WIDTH SCREENS.

5. SYSTEM ARCHITECTURE

5.1 REST API ENDPOINTS

  • REST ENDPOINTS: (LIST METHOD | URL | DESCRIPTION) — BASE URL: http://localhost:3001/api (A HOSTED URL WILL BE ADDED WITH #93)
  • PUBLIC ENDPOINTS:
    • POST /api/auth/register — CREATES AN ACCOUNT AND RETURNS A TOKEN (400 IF INVALID, 409 IF THE EMAIL IS TAKEN).
    • POST /api/auth/login — CHECKS THE HASHED PASSWORD AND RETURNS A TOKEN (401 IF WRONG).
    • GET /api/health — CONFIRMS THE API IS RUNNING.
  • PROTECTED ENDPOINTS (REQUIRE AUTHORIZATION: BEARER TOKEN; 401 WITHOUT A VALID ONE):
    • GET /api/auth/me — FETCHES THE LOGGED-IN USER.
    • PUT /api/auth/password — CHANGES THE PASSWORD; NEEDS THE CURRENT PASSWORD (400 IF IT IS WRONG OR THE NEW ONE IS INVALID).
    • DELETE /api/auth/me — DELETES THE ACCOUNT AND ALL OF ITS CATEGORIES, TRANSACTIONS, AND BUDGETS; NEEDS THE PASSWORD (400 IF WRONG).
    • GET /api/transactions?categoryId=&from=&to= — FETCHES THE USER'S TRANSACTIONS, NEWEST FIRST, WITH OPTIONAL FILTERS (400 FOR A BAD DATE OR AN UNKNOWN CATEGORY).
    • POST /api/transactions — CREATES A NEW INCOME OR EXPENSE (RETURNS 400 WITH A LIST OF ERRORS IF INVALID).
    • PUT /api/transactions/:id — EDITS A TRANSACTION WITH THE SAME RULES AS POST (404 IF IT IS NOT THE USER'S).
    • DELETE /api/transactions/:id — DELETES A TRANSACTION (404 IF IT IS NOT THE USER'S).
    • GET /api/budgets/summary — FETCHES MONTHLY TOTALS AND EACH CATEGORY'S LIMIT, SPENT, REMAINING, AND STATUS (OK / WARNING / OVER).
    • GET /api/reports/spending-by-category — FETCHES THE MONTH'S SPENDING PER CATEGORY, LARGEST FIRST, FOR THE CHART.
    • GET /api/categories — FETCHES THE USER'S INCOME AND EXPENSE CATEGORIES WITH THIS MONTH'S LIMIT.
    • POST /api/budgets — SETS A MONTHLY LIMIT FOR AN EXPENSE CATEGORY (409 IF ONE ALREADY EXISTS).
    • PUT /api/budgets/:id — CHANGES A BUDGET'S MONTHLY LIMIT.
    • POST /api/categories — CREATES AN INCOME OR EXPENSE CATEGORY (409 IF THE NAME IS ALREADY USED).
    • PUT /api/categories/:id — RENAMES A CATEGORY.
    • DELETE /api/categories/:id — DELETES A CATEGORY AND ITS BUDGETS (409 IF IT STILL HAS TRANSACTIONS).
    • GET /api/plaid/status — WHETHER BANK CONNECTIONS ARE ON, AND WHETHER THIS USER HAS CONNECTED A BANK (US-10).
    • POST /api/plaid/link-token — A SHORT-LIVED TOKEN FOR PLAID LINK (404 WHEN BANK CONNECTIONS ARE OFF).
    • POST /api/plaid/connect — EXCHANGES LINK'S ONE-TIME PUBLIC TOKEN AND STORES THE CONNECTION ENCRYPTED (502 IF PLAID FAILS).
    • POST /api/plaid/sync — IMPORTS NEW POSTED TRANSACTIONS; RETURNS HOW MANY WERE IMPORTED AND SKIPPED.

5.2 DATABASE SCHEMA (SUPABASE POSTGRESQL)

  • DEFINED IN packages/backend/src/db/schema.sql AND RUN ONCE IN THE SUPABASE SQL EDITOR. THE APP USES A HOSTED SUPABASE POSTGRESQL DATABASE, SO THE WHOLE TEAM (AND A DEPLOYED SERVER) SHARES ONE PERSISTENT COPY OF THE DATA. THE BACKEND CONNECTS WITH THE pg CLIENT USING DATABASE_URL, AND EVERY QUERY IS PARAMETERIZED ($1, $2, ...). AUTOMATED TESTS NEVER USE SUPABASE (SECTION 9). ROW LEVEL SECURITY IS ON FOR ALL FOUR TABLES WITH NO POLICIES, SO SUPABASE'S PUBLIC anon AND authenticated ROLES SEE NO ROWS; THE BACKEND CONNECTS AS THE TABLES' OWNER, WHICH IS NOT RESTRICTED.
TABLECOLUMNSKEYS / CONSTRAINTS
usersid, email, password_hash, name, created_at (TIMESTAMPTZ)PK id (INTEGER IDENTITY); email UNIQUE

transactionsid, user_id, category_id, type, amount_cents, date (DATE), note, created_atPK id; FK user_id → users (ON DELETE CASCADE); FK category_id → categories; type IN (INCOME, EXPENSE); amount_cents > 0; INDEX ON (user_id, date)
budgetsid, user_id, category_id, period (YYYY-MM), limit_amount_centsPK id; FK user_id → users (ON DELETE CASCADE); FK category_id → categories; period MUST BE YYYY-MM WITH A REAL MONTH; limit_amount_cents > 0; UNIQUE (user_id, category_id, period), SO ONE BUDGET PER CATEGORY PER MONTH
bank_connectionsid, user_id, item_id, access_token_enc, sync_cursor, created_atPK id; FK user_id → users (ON DELETE CASCADE), UNIQUE (ONE BANK PER USER); access_token_enc IS AES-256-GCM ENCRYPTED. transactions ALSO HAS plaid_transaction_id, UNIQUE PER USER, SO AN IMPORT NEVER REPEATS (US-10)

5.5 ACCESS CONTROL

  • DESIGN: SIGN-UP AND SIGN-IN RETURN A JWT THAT EXPIRES AFTER ONE DAY. THE FRONTEND STORES IT IN LOCALSTORAGE SO A PAGE REFRESH STAYS LOGGED IN, AND api.js SENDS IT AS AN AUTHORIZATION: BEARER HEADER WITH EVERY CALL. THE AUTHENTICATE MIDDLEWARE VERIFIES IT BEFORE ANY DATA ROUTE RUNS AND TAKES THE USER ID FROM THE TOKEN, NEVER FROM THE REQUEST BODY.
  • FAILURES: A MISSING, INVALID, OR EXPIRED TOKEN RETURNS 401, AND THE FRONTEND THEN CLEARS THE TOKEN AND SHOWS THE LOGIN PAGE. ANOTHER USER'S RECORD RETURNS 404, SO THE API DOES NOT REVEAL THAT IT EXISTS. A WRONG PASSWORD AND AN UNKNOWN EMAIL RETURN THE SAME MESSAGE.
  • OVERVIEW (SIGN-IN AND ADDING A TRANSACTION): DRAWN FROM THE REQUESTS THE RUNNING APP MAKES. IT REPLACES JUAN S.'S FIRST DRAFT (docs/architecture/sequence-overview-juan-s-draft.pdf), WHICH SHOWED A MICROSOFT SIGN-IN THE APP DOES NOT HAVE.

7. DATA REQUIREMENTS

7.1 LIST OF PERSISTENT DATA

  • USER ACCOUNT: EMAIL (UNIQUE), PASSWORD HASH (NEVER PLAIN TEXT), DISPLAY NAME.
  • CATEGORY: NAME (UNIQUE PER USER), TYPE (INCOME OR EXPENSE).
  • TRANSACTION: AMOUNT (> 0), TYPE, CATEGORY, DATE (A REAL CALENDAR DAY, STORED AS A POSTGRESQL DATE), NOTE (UP TO 200 CHARACTERS).
  • BUDGET: CATEGORY, MONTH (YYYY-MM), LIMIT AMOUNT (> 0); ONE BUDGET PER CATEGORY PER MONTH.
  • BANK CONNECTION (US-10): PLAID ITEM ID, ENCRYPTED ACCESS TOKEN, SYNC POSITION; ONE PER USER. IMPORTED TRANSACTIONS KEEP PLAID'S TRANSACTION ID. THE BANK PASSWORD IS NEVER STORED OR SEEN.
  • NOT STORED (COMPUTED ON REQUEST): MONTHLY TOTALS, REMAINING BALANCE, PERCENT OF BUDGET USED, BUDGET STATUS, SPENDING BY CATEGORY.

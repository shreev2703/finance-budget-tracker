LedgerLogic is a web app that helps college students log income and expenses, see their monthly balance, and stay under per-category spending limits, with a warning at 80% of a limit. This document records the architecture and design decisions we have made so far. Each item is labeled IMPLEMENTED (in the code on main) or PLANNED.

1. Proposed Architecture

Pattern: Layered architecture inside a client-server system IMPLEMENTED

The system is split into three tiers: a React client running in the browser, a Node.js/Express REST API server, and a relational database. Inside the server, the code is organized into strict layers. Each layer only calls the layer directly below it:

React client  →  Express middleware  →  routes (controllers)  →  services  →  repositories  →  SQLite / MySQL

Why it fits LedgerLogic.

  • The app is mostly CRUD plus a few business rules. A layered design gives each rule one obvious home. For example, the 80% budget warning (US-09) is defined once in domain/budget.js.
  • Three students work in parallel. The client and the server only share a JSON contract (the REST endpoints), so frontend and backend work can proceed independently.
  • It is easy to test. The whole API runs against an in-memory database in our automated tests (backend/test/api.test.js), because the database is passed into the app rather than hard-coded.
  • Microservices or event-driven designs would be overkill for a single-user budgeting app with four tables and no real-time features.

Communication direction: the client always starts the exchange (HTTP request); the server never pushes to the client. Within the server, calls only go downward (routes → services → repositories → database), and results return up the same path.

External systems: none. Bank linking, automatic transaction import, and payments are explicitly out of scope in our SRS, and we build login ourselves (see Decision 4), so the app has no third-party services.

2. High-Level Design

Client side IMPLEMENTED (prototype)

The React prototype (built with Vite) has these main pages: Login, Dashboard (monthly budget card, category allocation bars with amount remaining, recent transactions), Transactions (full history), and Create / Edit Category (name + monthly limit). App.jsx holds the shared state (the current page and the list of categories) and passes it to each page as props. Juan F.'s component plan (frontend-architecture.md) sets the target structure: App → DashboardPage → BudgetSummary, TransactionList, AddTransactionForm, with DashboardPage owning the shared data and refreshing it after a transaction is added.

The current prototype uses sample data in React state. Planned: a small API client module (fetch('/api/...')) that loads real data from the backend, plus a Vite proxy that forwards /api to port 3001.

Key data flow: adding an expense

  1. The student submits the Add Transaction form; the client sends POST /api/transactions with { amount, type, categoryId, date, note }.
  2. Middleware parses the JSON and attaches the user ID.
  3. TransactionService validates every field, checks that the category belongs to the user and matches the type, and converts dollars to cents.
  4. TransactionRepository inserts the row; the API returns 201 with the saved transaction (or 400 with a list of problems).
  5. The client re-requests GET /api/budgets/summary, so the balance and category bars update. A category at or above 80% of its limit is flagged warning, and one above 100% is flagged over.

3. Design Pattern: Chain of Responsibility IMPLEMENTED

Category: Gang of Four, behavioral pattern.

Problem it solves

Every API request needs the same cross-cutting steps before and after the actual work: parse the JSON body, figure out which user is calling, find the matching route, answer with a 404 if nothing matched, and convert any thrown error into a clean JSON error with the right status code. If every route did these steps itself, the same code would be copied into every endpoint, and changing one step (for example, replacing our temporary demo user with real login) would mean editing every route.

How we apply it

Chain of Responsibility passes a request along a chain of handlers. Each handler either handles the request or passes it to the next one. Express middleware is this pattern. Every handler has the same interface, (req, res, next), and calls next() to pass the request on, or next(err) to jump to the error handler. We build the chain once in backend/src/app.js:

// packages/backend/src/app.js (lines 17–32)
const app = express();
app.use(express.json());              // 1. parse the JSON body          → next()
app.use('/api', demoUser(db));        // 2. attach req.userId            → next()
app.use('/api', apiRouter({ ... }));  // 3. run the matching route, or   → next()
app.use(notFound);                    // 4. no route matched → 404 JSON
app.use(errorHandler);                // 5. any next(err)/throw → 4xx/500 JSON
// packages/backend/src/middleware/demoUser.js
export function demoUser(db) {
  const findUser = db.prepare('SELECT id FROM users WHERE email = ?');
  return (req, res, next) => {
    req.userId = findUser.get(DEMO_USER_EMAIL)?.id;  // handle my part...
    next();                                           // ...then pass it on
  };
}
GoF roleOur codeWhat it does
Handler (interface)(req, res, next) function signatureThe common interface every link implements
Concrete handlersexpress.json(), demoUser, apiRouter, notFound, errorHandlerEach does one job, then calls next() or ends the request
Client / chain buildercreateApp() in app.jsPuts the handlers in order
Successor linknext() / next(err)Passes the request on, or skips straight to the error handler

Why this beats one large module

  • One job per handler. Each handler is a few lines and can be read and tested on its own. One large request-handling function would mix parsing, identity, routing, and error formatting together.
  • Swappable links. When we build login (US-07), we replace demoUser with an auth handler that checks a session or token. No route or service changes.
  • Consistent errors. Every error in the app takes the same path to errorHandler. The frontend always receives { error, details }, so it can show validation messages the same way on every form.
  • Easy to extend. Future handlers such as request logging or rate limiting can be inserted at the right point in the chain without touching existing code.

4. Design Decisions and Tradeoffs

Decision 1: Separate service and repository layers instead of putting logic in Express routes

Options considered(a) Write SQL and validation directly inside each route handler. (b) Routes → services → repositories.
Selected(b) Routes only translate HTTP; services hold validation and business rules; repositories hold all SQL.
Why it fits nowIt costs a few more files, but rules like "the category must match the transaction type" and "warn at 80%" live in one place. The SQL can change (SQLite → MySQL) without touching the routes. It also lets us test the full API automatically, which matters because our Project Tester role is responsible for verifying each feature.

Decision 2: SQLite now, MySQL-compatible schema for later

Options considered(a) MySQL server from day one (as listed in the SRS template). (b) MongoDB. (c) SQLite through Node's built-in node:sqlite, with a schema written to map 1:1 to MySQL.
Selected(c) SQLite for development and demos.
Why it fits nowNo database server has to be installed on any teammate's laptop or the presentation machine, so npm install then npm run dev just works. The data is relational (users → categories → transactions/budgets), so a SQL database suits it better than MongoDB. Because all SQL sits in the repository layer, moving to MySQL later is contained to repositories/ and db/. Tradeoff: SQLite is not built for many simultaneous writers, which is fine at our scale.

Decision 3: Store money as integer cents

Options considered(a) JavaScript floating-point numbers. (b) A DECIMAL column. (c) Integer cents (amount_cents), converted at the API edge.
Selected(c) Integer cents. The API accepts dollars in requests and returns …Cents fields.
Why it fits nowFloating-point math gives answers like 0.1 + 0.2 = 0.30000000000000004, which would make totals and the 80% threshold slightly wrong. Integers are exact in both SQLite and JavaScript. Tradeoff: the frontend has to divide by 100 when displaying amounts.

Decision 4: Build our own login later; use a demo user for now PLANNED

Options considered(a) A hosted auth service (Supabase Auth, Firebase Auth). (b) Our own email + password login with bcrypt hashing and a session/JWT middleware. (c) Build auth before any other feature.
Selected(b), scheduled after the core budgeting flow. Until then, a demoUser middleware acts as one seeded student.
Why it fits nowOur SRS promises privacy and no third-party accounts, and it already requires bcrypt hashing. Our users table (email, password_hash) is ready for it. Building the budgeting features first let us demo real value sooner. Thanks to the Chain of Responsibility design, adding login means swapping one handler.

Decision 5: Shared state in the top-level React component instead of a state library

Options considered(a) A global store such as Redux. (b) Keep shared data in one parent component (App / DashboardPage) and pass it down as props.
Selected(b), per Juan F.'s frontend architecture plan.
Why it fits nowThe app has a handful of pages sharing two pieces of data (categories and transactions), so a store library would add setup without benefit. When the parent's state changes after a save, React re-renders every component that uses it, so the list and the budget bars stay in sync automatically.
